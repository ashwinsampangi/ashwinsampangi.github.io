Some instructions expire

Instructions written to fix an older model can do nothing for the current one, or work against it. A small, fixed test gives evidence for which lines to keep and which to delete when the model changes.

Ashwin Kumar · 26 October 2026

A finance team that runs AI on its recurring work builds up instructions, templates, saved prompts and scheduled automations, and some of them may now do nothing for the model in use, or work against it. A small test, kept fixed and rerun whenever the model or an instruction changes, gives evidence for which to keep and which to delete. Each instruction line is first tagged by what it is for: capability, context or governance, and a line that does two jobs is split so that each part carries one tag. Capability lines are the ones tested for removal; context and governance lines change when a fact or a rule changes.

Many instructions were written to fix a failure of the model then in use, such as a table in the wrong order or a figure with no source. The models underneath change on a cycle of months, and the instructions written for older ones tend to stay, because a line that no longer helps seldom causes a visible error. So the library grows by addition, and often nothing in the workflow prompts a re-test.

Lines that duplicate the model's defaults end up beside lines carrying facts it cannot know, often with nothing to tell them apart. A stale line can override a better default, and when a threshold changes, the line that carries it is harder to find.

Under a controls framework, finance already reviews its controls on a cycle, often yearly, and can retire controls that no longer address a risk. An instruction library that shapes reported figures, or the commentary on them, should be reviewed the same way, on a shorter cycle, because the model underneath it changes more often than the risks do.

Deleting a line moves the risk it covered onto the model, which is why the test has to be rerun. Where a control relies on the model's output, any change to the instruction lines or to the model can change how that control performs, so each should go through the same change approval as any other change to the control. The test run, the approval and a record of who reviewed the results are among what an auditor testing the change would ask to see.

In an instruction set for drafting monthly variance commentary, a line asking for full sentences may have been written to fix an earlier model's bare lists of movements. A current model may write in sentences unprompted, though some still default to lists, so the line is a candidate for the test rather than for deletion on sight. A line that caps each driver at one sentence takes its tag from what it is for. If it is there only to stop an earlier model from running long, it is capability and goes through the test, since it may now cut off a second cause the model would otherwise name. If the board asked for one sentence per driver, the line is context and stays, as is a line setting a table layout the board expects every month. A passing test shows that the model does something unprompted; it does not show whether the team still wants it, so the tag is decided first.

Context lines carry what the model cannot know, such as the materiality threshold or the reporting names for cost centres; governance lines carry rules the team keeps however capable the model becomes, such as every figure tying to the attached ledger extract, with any figure that cannot be tied flagged rather than estimated. The tie-out itself is still checked outside the model, and governance rules are checked there wherever they can be.

Corrections already recorded as dated, sourced precedent, as in the earlier note Corrections as case law, take the same tags. One tagged as capability can be retired like any other line, and it keeps its record, dated with the model and the test run behind it, so the next person can see why it went and reinstate it if the failure returns.

The test is a small, fixed set of cases from the team's own recurring work. A case is an input with a known right answer, such as a closed month's variance file with the commentary a reviewer approved, plus a short note of what a passing output must get right, since a draft will rarely match the approved text word for word. The cases hold real data, so they sit under the same access rules as the work and go only to tools approved for that data. Three to five cases per recurring task is a reasonable start, and a new case is added when a failure appears that none covers.

At least one case should contain a known error: a marked test copy of a finished document, with one figure changed so that it contradicts another on the same page. Given to the reviewing tool with its usual instruction, it should come back with the contradiction named. That planted-figure case is the test the September piece asked readers to run.

The team reruns the set at every model change, every instruction change and before each quarter-end close, because a vendor can update a model, or the instructions its product adds, without notice. A change made without notice cannot go through change approval, so the scheduled rerun is the check that can find it. Pinning a model version, where the vendor offers it, holds the model but not a product's own instructions, and a hosted pinned version is still retired on the vendor's schedule.

Capability lines come out one at a time, so that a new failure can be traced to the line removed. A line comes out only when the set holds a case for the failure it was written to fix, and that case passes without the line on each of at least five runs, since the same input can give different output from run to run. Every other case in the task's set must also pass without it on one run: that catches a removal that breaks them outright, and a rarer effect is left to the scheduled reruns and to the rule that puts a line back. Where no one recorded what a line was written to fix, the owner of the output is first asked whether it states a requirement; if it does not, the case is built from what the line demands, such as a draft that explains each variance in full sentences, and the line is tested against that case like any other. A retired line is recorded with the date, the model and the runs behind it.

If each run is an independent draw, a five-run test will catch a failure that appears in half of all runs about 97 times in 100, but where the failure appears once in twenty runs, the case would still pass all five more than three times in four. Where a tool returns the same output for the same input every time, five runs carry the evidence of one, and the test needs more cases rather than more runs. So the line goes back in the first time its failure returns, or a new failure is traced to its removal, in the set or in live work, and a failure seen first in live work becomes a new case.

Scheduled automations need the same review. A team can reasonably set a rule that a check finding no exceptions over a set run of periods, such as a full year for a monthly check and longer where the risk is rare, comes up for retirement review. That review asks whether the risk is still present, because an empty result can mean a clean process, a process kept clean by the check itself, a risk that did not arise, or a check that has stopped looking. A planted case, run on a test copy rather than the live records, shows whether the check is still looking. A check that enforces a governance rule stays while the rule stands.

Someone has to build the cases, keep the known answers current and rerun the set at each model change, and that work falls on people who already have a close to run. Whether it pays depends on what the output feeds. For commentary that reaches a board or a lender, one wrong sentence in front of that reader is likely to cost more than the reruns. For an internal summary, a lighter test may be enough. A tagged library is also easier for a new owner to take over, because each line shows what it is for. Rewriting the library from scratch at each model change skips the tagging, but it can drop context and governance lines along with the stale ones unless someone sorts them first, which is the tagging under another name.

I would start with the longest instruction set among the tasks whose output reaches a board or a lender, because that is where old fixes are most likely to have piled up and where one wrong line costs more. Finance should tag that set line by line, name one owner for it, build its cases from recent closes, and run them now, so that there is a baseline when the next model change arrives.

What came back

The 28 September field note, The reviewer who always agrees, asked readers to plant a contradicting figure in a finished document, run it past their automated reviewer, and report whether the reviewer caught it. I said I was keeping a tally and would publish what it showed in the next note.

By 26 October, when I closed the count, no results had come back in the comments and messages I could check.

That empty count says nothing about automated reviewers, because none was measured. The ask may have reached few readers, and some who saw it may have had no automated reviewer to test. My guess, which I cannot test, is that I also asked for a lot, and the last part most of all: a report, in a comment or to a stranger, that could amount to saying your own control failed.

If you have not run the planted-figure case yet, the steps are in the paragraph on known errors above, and running it does not require reporting the result to anyone. A reviewer that caught the planted figure once has passed a single run, which is why the case stays in the set for the next model or instruction change.
